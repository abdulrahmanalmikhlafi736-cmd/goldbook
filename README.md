# FPRO — أندرويد / Kotlin / Jetpack Compose

عميل ويب مستقل باللغة العربية لفيسبوك، الإصدار **0.0.1**، الحزمة **com.almekhlafi.FPRO**، المطور **عبدالرحمن المخلافي**. Android 6.0 (API 23) فأحدث. ترخيص الشيفرة الجديدة GPL-3.0، انظر [LICENSE](LICENSE). ليس منتجاً رسمياً لفيسبوك ولا تابعاً لشركة Meta.

## البناء وإنتاج APK

1. ثبّت Android Studio مع **JDK 17** وAndroid SDK Platform **35**، واقبل تراخيص SDK.
2. افتح هذا المجلد كمشروع Gradle. اجعل Android Studio ينشئ `local.properties` الذي يشير إلى SDK، أو عيّن `ANDROID_HOME`.
3. من جذر المشروع:

```sh
./gradlew testDebugUnitTest lintDebug assembleDebug
# Windows: gradlew.bat testDebugUnitTest lintDebug assembleDebug
```

الناتج القابل للتثبيت والموقّع بمفتاح التطوير: `app/build/outputs/apk/debug/app-debug.apk`.

```sh
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

بناء المتجر: استخدم **Generate Signed Bundle / APK** في Android Studio مع مفتاحك الخاص. لا تستخدم مفتاح التطوير للنشر ولا ترفع مفاتيحك إلى Git. `assembleRelease` وحده ينتج إصداراً غير موقع؛ لا يحتوي المشروع على مفاتيح إنتاج.

يوجد Workflow في `.github/workflows/android.yml`: عند دفع التغييرات إلى GitHub أو تشغيله يختبر ويبني ويرفع APK إلى **Artifacts → FPRO-0.0.1-debug**. هذا ملف بناء مُعدّ للتنفيذ وليس ادعاءً بأنه نُفّذ بالفعل.

## ما ينفذه المشروع

- واجهة أصلية بـCompose وMaterial 3 واتجاه RTL، إعدادات محفوظة، شاشة افتتاحية ذهبية بخمس نقاط متحركة مخصصة (ليست أصلاً رسمياً من Meta).
- WebView واحد يحفظ الجلسة والكوكيز، رفع الملفات عبر منتقي النظام، معالجة أخطاء الشبكة دون تجاوز أخطاء TLS.
- الموقع يملأ مساحة التطبيق مع زر ⚙ عائم فقط؛ أزيل شريط FPRO وزرا فيسبوك والرسائل. قوائم الموقع الأصلية هي وسيلة التنقل. الزر العائم ليس جزءاً من DOM الخاص بشعار Meta.
- خيارات مستقلة للإعلانات والمقترحات والريلز والقصص والأشخاص والمجموعات، عبر مرشحات DOM محدودة ومراقب تغييرات مؤجل.
- 12 اختياراً لونياً حسب الأسماء المذكورة في الطلب (القائمة المطلوبة احتوت 12 اسماً لا 11)، الوضع الداكن وAMOLED، Material You على API 31+ لواجهة Compose. تلقائي لا يغير ألوان الموقع. ألوان الموقع عبر CSS اجتهادية وليست إعادة تلوين كاملة مضمونة لكل نسخة.
- مطابقة لون الشريط مع `theme-color` أو خلفية الصفحة عند اكتمال التحميل، وليس مراقبة مستمرة لكل تغير لوني.
- زر تنزيل شفاف على عناصر HTML video، تحريك بالضغط 400ms ثم السحب، حفظ الموضع النسبي لحاوية الفيديو في تخزين أصل الموقع، مشاركة الرابط إلى الحزمة المحددة.
- التنزيل خارجي فقط إلى الحزمة المحددة ونافذة Seal السريعة؛ لا قائمة تنزيل داخلي ولا نقل لكوكيز الحساب إلى أداة التنزيل.
- تقدم فيديو بألوان قوس قزح وكرة، تحديد النص حيث تسمح الصفحة، تكبير اختياري، تثبيت banner حيث توفره الصفحة، وضع سطح مكتب، عكس الاتجاه.
- التنقل في فيسبوك ورسائل الويب ضمن WebView نفسه دون شريط أزرار بديل، ملء شاشة الفيديو بالنقر المزدوج، وضع مغمور، رجوع يغلق واجهة الإعدادات/التنزيل/الفيديو/حوار الصفحة المعروف ثم يصعد لأعلى ثم يعود في السجل ثم يغلق التطبيق.
- PiP على Android 8+ عند وجود فيديو يعمل وفق دعم النظام. زر السماعة يحول إلى صوت فقط ويخفي النافذة بخدمة foreground وإشعار للتحكم، أو يمكن اختياره من الإعدادات على Android 6+. قفل الشاشة مدعوم في الاختبار المحلي؛ إنهاء الصفحة/التطبيق أو الخدمة/قيود النظام أو الموقع قد ينهي التشغيل.
- روابط خارجية إلى التطبيقات/المتصفح، بطاقة المطور ورابط واتساب `+967781764759`.

## قيود لا يمكن حلها بوعد برمجي

1. **WebView ليس تطبيق Meta الرسمي.** تسجيل الدخول والرسائل والريلز والقصص والتعليقات تعتمد على ما يقدمه الموقع لحسابك وWebView لديك. يمكن لفيسبوك منع الدخول أو طلب فتح تطبيقه أو تغيير بنيته؛ لا يمكن تجاوز سياساته أو المصادقة. لا يوجد ضمان أداء «صفر تهنيج» أو سرعة أعلى دائماً من المتصفح.
2. **الحزمة ليست API.** ACTION_SEND يشارك رابطاً فقط ويخرج إلى التطبيق المستهدف. لا يستطيع أندرويد إدراج Activity تطبيق آخر داخل FPRO أو قراءة قائمة تنزيلاته وتقدمه دون تكامل موثّق منه. لا توجد هنا قائمة تنزيل داخلي أو قائمة مزيفة للتطبيق الخارجي. لا يتم ادعاء العكس أو إنشاء تقدم وهمي.
3. **ليس كل فيديو قابلاً للتنزيل.** روابط `blob:`/MediaSource والبث المجزأ/DRM والقصص المصورة ليست ملفات MP4 مباشرة. لا يوجد استخراج محمي أو تجاوز حماية، وقد تنتهي صلاحية روابط CDN. لا يوجد ضمان تنزيل أي فيديو/ريلز/ستوري. زر التنزيل يقرأ مصدر الفيديو الحالي أو هويته/رابطه المحلي المثبت. لا يرجع إلى رابط الصفحة القديم عند غياب هوية موثوقة، ولا يرسل الكوكيز إلى تطبيق التنزيل.
4. **الإعلانات بكل اللغات ليست قابلة للتحديد المضمون.** توجد مطابقة لعناوين عربية مع إزالة التشكيل والتطويل، وإنجليزية وألمانية وفرنسية وإسبانية وإيطالية لبعض العناوين. لا يوجد ادعاء بتغطية كل اللغات/التقسيمات المتعمدة للنص. الحجب لا يعترض الشبكة ولا يعطل إعلانات الفيديو المحمية.
5. **لا يوجد نظام push أصلي لإشعارات Meta.** تبقى إشعارات الموقع داخل الصفحة وفق ما يتيحه؛ ليست إشعارات حساب تصل بعد إغلاق التطبيق. الصوت الخلفي في25 خدمة تشغيل يبدؤها المستخدم، لا خدمة إشعارات Meta، ولا يستمر بعد إنهاء التطبيق/الخدمة أو قتل العملية. مكالمات الميكروفون/الكاميرا غير مدعومة؛ أذونات WebRTC مرفوضة عمداً. يمكن رفع صور وملفات موجودة عبر منتقي النظام.
6. تكبير بعض صفحات الهاتف، تحديد النص، تثبيت شريط Meta، CSS الداكن وملء الشاشة قد تتأثر ببنية الصفحة وسياساتها. لا يوجد شريط تنقل أصلي إضافي؛ خيار sticky يحاول تثبيت شريط الموقع نفسه.

إذا كان اشتراط «كل الميزات بلا استثناء» حرفياً، فهذا المشروع **لا يحقق ذلك الاشتراط**: يحتاج بعضه API من التطبيق الخارجي وMeta وبعضه تمنعه قيود النظام/الموقع. لا توجد شيفرة وهمية تُخفي هذه الحدود.

## البنية والأمان

- `MainActivity.kt`: دورة حياة WebView، Compose، التنقل، منتقي الملفات، الفيديو وPiP.
- `SettingsPanel.kt` / `Preferences.kt`: الإعدادات والتخزين المحلي.
- `DownloadStore.kt`: التنزيلات الحقيقية والاستعلام عن حالة النظام.
- `assets/facebook.js`: CSS وDOM وفيديو؛ حقن متكرر آمن دون تكرار المراقبين.
- لا `addJavascriptInterface` مكشوف، ولا وصول إلى ملفات الجهاز من الويب، ولا HTTP cleartext، ولا خادم يجمع بيانات تسجيل الدخول. تبقى الجلسة في تخزين WebView المحمي بعزل أندرويد. النسخ الاحتياطي معطل. لا تُعطل TLS أو Safe Browsing.
- فحص المضيف يعتمد على حدود النطاق، لا احتواء النص. المخططات الخارجية محدودة بـhttp/https/mailto/tel. المشاركة والتنزيل إجراءات يوافق عليها المستخدم.
- الأرشيفات وملفات DEX الموجودة مسبقاً في المستودع لم تُستخدم ولم تُعدّل؛ المشروع الجديد ليس إعادة تجميع لشيفرتها مجهولة المصدر أو ترخيصاً لها.

## تشخيص الشاشة الرمادية

- هوية WebView الأصلية هي الافتراضية. يوجد خيار توافق متصفح اختياري؛ لا يُفرض انتحال هوية Chrome على الموقع.
- تعديلات DOM والمرشحات وألوان الموقع وأدوات الفيديو معطلة افتراضياً، وتتطلب تفعيل «أدوات وتعديلات الصفحة». تعطيلها بعد استخدامها يعيد تحميل الصفحة الأصلية.
- أثبتت لقطات التشغيل 39899234428 أن الحاوية الأصلية ترسم نموذج الدخول بينما الحاوية السابقة بقيت بيضاء رغم وجود نصوص وحقول في DOM. الإصدار 7 يفصل WebView في FrameLayout أصلي، ويستخدم Compose كطبقة تحكم شفافة، ويؤخر بدء التحميل حتى تركيب الحاوية وزوال شاشة البدء. نجح اختبار APK المصغر على Android 15 و16 في التشغيل [39900288305](https://github.com/abdulrahmanalmikhlafi736-cmd/goldbook/actions/runs/39900288305)، بما فيه رسم الصفحة المحلية وظهور عناصر فيسبوك الحقيقية. صُحّح سباق توقيت الاختبار المحلي مع شاشة البدء، ثم نجحت جميع وظائف مصفوفة الأجهزة في التشغيل [39900957233](https://github.com/abdulrahmanalmikhlafi736-cmd/goldbook/actions/runs/39900957233)، بما فيها لمس حقل الدخول والتركيز عليه دون إدخال بيانات حساب. لا تزال تجربة الهاتف والحساب المسجل غير مؤكدة.
- المهلة الأصلية كانت تتوقف على استجابة JavaScript؛ أصبح فحص التعطل الأصلي يعمل حتى إذا لم يصل رد JavaScript أو لم يُرسل `onPageStarted`. يحاول تأكيد وجود نص بعد 24 ثانية ثم يعرض تشخيصاً بعد ثانية إضافية عند عدم التأكيد. تأكيد النص في DOM **ليس ضماناً لرسم بكسلات على كل جهاز**.
- تتضمن الإعدادات إصدار مزود WebView وحالة التحميل والعنوان وأبعاد WebView، وزر نسخها. راجع معلومات العنوان قبل مشاركتها، فقد يحتوي رابط الموقع على بيانات شخصية؛ لا يسحب التطبيق كلمات المرور أو الكوكيز إلى التشخيص.
- يوجد اختبار محلي أخضر عبر الإعدادات، مستقل عن الإنترنت، مكتوب بصياغة JavaScript قديمة متوافقة. **ليس صفحة فيسبوك مزيفة**؛ وظيفته فصل أعطال الرسم عن أعطال اتصال الموقع. يوجد خيار للرسم البرمجي للأجهزة التي تعرض سطح WebView رمادياً؛ قد يخفض أداء الفيديو، لذا لا يُفرض على الجميع.

### اختبارات عرض حقيقية، لا نجاح تجميع فقط

يضيف `.github/workflows/device.yml` اختباراً على محاكيات Android 10 وAndroid 15 وAndroid 16:

- `app/src/androidTest`: عرض صفحة HTML محلية داخل WebView وفحص بكسلات الشاشة وتنفيذ JavaScript، دون الاعتماد على فيسبوك.

- تحفظ لقطات الشاشة والتقارير في Artifacts. عند نجاح الاختبار المصغر فقط، ينشر نفس APK الذي جرى اختباره باسم **`FPRO-compact-device-verified-API35`** أو **`FPRO-compact-device-verified-API36`** بحسب بيئة التحقق. لا تعتبر مجرد وجود artifact تشخيصي دليلاً على نجاح الاختبارات؛ راجع نتيجة التشغيل.

```sh
./gradlew :app:connectedDebugAndroidTest
./gradlew :device-tests:connectedCompactAndroidTest
```

تحتاج هذه الأوامر جهازاً/محاكياً مناسباً وSDK. فحص فيسبوك الحي يتطلب اتصالاً وقد يتأثر بتغييرات الموقع. الاختبارات لا تتحقق من تسجيل الدخول بحساب أو الرسائل/الفيديوهات المحمية، ولا تثبت سبب الشاشة الرمادية على هاتف لم نقرأ تشخيصه بعد. الفشل الأول لاختبار المحاكي استخدم صياغة JavaScript غير مدعومة في مزوده القديم؛ صُحّح الاختبار، ولا يُنسب ذلك الفشل وحده إلى فيسبوك أو الهاتف.

## البناء 16 — سرعة الهاشتاج وتشخيص العوائق المتبقية

## البناء 17 — خلفية SVG للحلقة والرموز الخطية

تقرير المستخدم 16 أكد تفعيل الأحمر والتجربة و12 تفصيلًا نصيًا ملونًا، لكنه لم يعرض حدودًا/ظلالًا/تدرجات/عناصر SVG زرقاء في أغلفة صور 41→53 و38→50 بكسل. هذا يستبعد تلك الخصائص في العناصر المبلغ عنها فقط؛ لا يثبت غياب أي عنصر شقيق أو أن اللون مدمج في صورة الحساب. التقرير السابق لم يصف نوع background-image، لذلك لا يجوز اعتباره تشخيصًا نهائيًا.

- دعم خلفيات `data:image/svg+xml` المشفرة بالنسب أو Base64 على غلاف الصورة أو طبقة pseudo. يقتصر على إطار صغير ومحتوى متجهي محدود، ويغيّر stroke الأزرق فقط مع الحفاظ على الشفافية. يصبح SVG المضمّن دليلًا على استدارة الزخرفة دون اشتراط border-radius للغلاف المربع.
- لا تُطلب روابط بعيدة ولا تُفلتر صور الحساب. الخلفية الأصلية لا تُعاد كتابتها؛ يستخدم FPRO متغيره/قاعدته القابلين للإزالة. الخلفية المتجهية الأصلية لصورة مستقلة ليست إطارًا لمجرد كونها SVG: تعديل الخلفية نفسها يتطلب صورة ابن. SVG يحوي image أو text أو script أو عناصر غير مسموحة أو مراجع href/url يُرفض بدل المساس بصورة أو مورد خارجي.
- دعم صغير لرمز أزرق من نطاق Unicode الخاص (PUA) بجوار نص صاحب حساب، في حاوية نصية/رابط مناسبة أو بتسمية توثيق، مع استبعاد التنقل والأزرار. لا يفترض أن كل span بحجم 17px هو توثيق، ولا يصبغ صور شارات غير معرّفة. تتضمن المعالجة لون inline المهم عند انطباق هذه القاعدة.
- أضيف للتشخيص نوع خلفية كل مستوى وطبقتيه (`none`, `embedded-svg`, `embedded-raster`, `remote-url`, `gradient`, `other`)، وعلم كون العنصر الأزرق رمز PUA. لا يُنسخ عنوان الخلفية أو نص SVG أو حرف الرمز أو بيانات الحساب. لم يتغير المسار السريع للهاشتاجات الذي أكد المستخدم نجاحه.

**الاختبارات:** DOM يغطي SVG المضمّن على غلاف مربع، رفض صور SVG المضمّنة والمراجع الخارجية وصورة SVG مستقلة، الاستعادة والخصوصية ورمز مؤلف خطي مع أولوية مهمة وحماية التنقل. اختبار Android 15 يطابق هندسة 53/41 في حالة محلية: بكسل إطار SVG صار أحمر وبكسل الصورة الداخلية بقي أخضر، إضافة إلى كل اختبارات الهاشتاج/الحلقات/الصور/الطي السابقة.

واجهت محاولات الاختبار الأولى تعثرًا في جاهزية الصفحة المحلية ثم بكسل شارة أبيض قبل وصولها لاختبار الحلقة الجديدة. حُسّن إعداد الاختبار: ينتظر بدء التنقل الأول المؤجل من Compose قبل استبداله بالصفحة المحلية حتى لا يستبدلها لاحقًا، ويتحقق من علامة الصفحة واكتمال صورها بدلاً من الاعتماد على نوم ثابت أو onPageFinished فقط. لم تُغيّر معايير ألوان البكسلات ولم تُعتبر تلك المحاولات ناجحة. التغييرات الأخيرة خاصة بالاختبار، لا تعديل لتوقيت بدء التطبيق في الإنتاج.

**النتيجة النهائية:** المصدر `8ac2855`، البناء 40003614225 ناجح، جميع أجهزة 40003614218 ناجحة. API35 compact artifact `12522609564` ZIP 957153 بايت؛ API36 `12523851190` ZIP 957150 بايت. لا يزال تحقق المستخدم من الحلقة الفعلية مطلوبًا؛ لا ضمان بأن الخلفية SVG أو بأن شارة التوثيق PUA. إذا استمر اللون الأزرق يفيد نوع الخلفية الجديد في استبعاد هذا الاحتمال بدل تكراره.


## البناء 18 — فحص Canvas الزخرفي دون إعادة كتابة بكسلاته

- تقرير 17 أظهر أن أنواع الخلفيات المفحوصة كلها `none` ولم تطابقها قواعد SVG. لا يعني ذلك أن الحلقة جزء من صورة الحساب؛ لم يكن التقرير السابق يحصي Canvas.
- فحص محدود لطبقات Canvas المجاورة للصورة، بما فيها صف عريض بحلقة صغيرة مزاحة. لا يلوّن إلا طبقة مقروءة ذات مركز شفاف ورسم أزرق حلقي محلي، مع حدود للحجم والنطاق والطلاء خارج الحلقة. يرفض المركز المصمت/الصور والطبقات غير المقروءة أو ذات المرشحات الأصلية.
- نسخة قراءة في Canvas منفصل؛ لا يطلب سياق رسم المصدر، ولا يكتب بكسلاته، ولا يجلب صورًا أو يتجاوز CORS. مرشح SVG خاص يستبدل الأزرق وحده ويحفظ ألفا؛ يترك الرمادي والأخضر وغير الأزرق كما هو، حتى عند إعادة رسم حالة المشاهدة دون تغيير DOM.
- تقرير خاص `canvasLayers`: أبعاد وعدّ وقراءة/مطابقة/شفافية فقط، بلا مصفوفات بكسلات أو صور أو URLs أو محتوى حساب. عدم المطابقة ليس دليلًا على أن الحلقة مدمجة بالصورة.
- اختبارات DOM: حلقة صغيرة وصف 398×53 بمصدر 796×106، رفض Canvas المصمت وغير المقروء، عدم لمس سياق المصدر وبكسلاته، إزالة التلوين عند إعادة الفحص الرمادي، الاستعادة والخصوصية. اختبارات WebView debug على API29/35 قاست بكسلات الحلقة الحمراء والصورة الخضراء الأصلية والطبقة المصمتة الزرقاء وحالة إعادة الرسم الرمادية. API35 compact اجتاز اختبارات الواجهة الواقعية؛ API36 compact فشل فتح التطبيق ولا ندعي نجاحه. فحص الأدلة الإضافي: [40008168963](https://github.com/abdulrahmanalmikhlafi736-cmd/goldbook/actions/runs/40008168963).
- لم يتغير مسار الهاشتاجات السريع أو ⚙️ أو طي القصص أو تنزيل الفيديو الحالي عبر Seal أو ملء الشاشة. لا يوجد إثبات حتى الآن أن Canvas هو رسم الحلقة أو أن شارة الحساب الفعلية تطابق القواعد الحالية.


## البناء 19 — بدء أسرع وعمل أقل أثناء تقليب الفيديوهات

- يبدأ `loadUrl` واستعادة الجلسة مباشرةً بعد إنشاء الواجهة، بدل تأخيرهما 1800ms. تعرض شاشة البداية فوق التحميل لمدة 600ms؛ لا تؤخر طلب الموقع. لم يتغير حفظ الجلسة أو مصدر فيسبوك أو الأمان.
- أحداث التمرير تحافظ على تحديث موضع أدوات الفيديو في animation frame واحد، لكن تؤجل الفحص الشامل إلى 350ms بعد آخر حركة. لا تتكرر مهام الفحص الشامل كل 350ms أثناء استمرار الحركة. تظل مسارات MutationObserver والهاشتاجات الفورية مستقلة.
- إعداد الفيديو/التنزيل وحده لا يطلب قائمة نصوص الحجب الكبيرة. تستخدم قراءة العلامات `textContent` بدل `innerText` لتجنب طلب layout ضمن قراءة كل علامة؛ اختبارات الحجب والاستعادة باقية.
- تستبعد الفيديوهات خارج الشاشة قبل computed-style/ancestor walks وhit-testing، وتخفي أدواتها دون إعادة قياسها وكتابة مواضعها. لا يغيّر التطبيق مصدر الفيديو أو يمسح الكاش أو يفرض التحميل المسبق/الجودة أو يوقف فيديو المستخدم.
- فحص موضع ⚙️ يبقى 650ms عند ظهوره، ويصبح 1200ms عند غيابه؛ يتوقف استدعاء JavaScript لهذا الفحص عندما تكون نافذة التطبيق غير مركّزة أو الإعدادات مفتوحة.
- الإعدادات: عنوان وزر رجوع ثابتان، بطاقات مستديرة بألوان Material 3 وتباعد وتوسيط أفضل للمفاتيح، مجموعات الفيديو/التنزيل/المظهر/الحجب/الأدوات، ثم التوافق والتشخيص وبطاقة المطور. جميع المفاتيح والقيم المحفوظة موجودة. نقل التشخيص لأسفل استلزم تحديث اختبار الجهاز لبلوغه بتمرير حقيقي بدل افتراض وجوده أول الشاشة.
- اختبارات DOM الجديدة تثبت بقاء مؤقت فحص شامل واحد بعد 20 حدث تمرير، وعدم تشغيله قبل هدوء الحركة، وتلوين هاشتاج جديد في microtask أثناء الانتظار، وتجاوز query النصوص في وضع الفيديو فقط، وعدم hit-testing/computed-style للفيديو خارج الشاشة. كل الاختبارات السابقة ناجحة.
- الجولة الأولى 40019844866 نجح فيها debug API29/35، وفشل compact API35/36 لأن اختبار التشخيص كان يفترض أنه أول الشاشة. بعد تعديل مسار الاختبار فقط نجح API35 compact في الجولة 40020914457؛ API36 فشل فتح التطبيق في هذه الجولة. لا يُحسب نجاحًا ولا تُنسب مشكلته إلى سبب غير مثبت.
- التحسينات تقلل أعمالًا معلومة داخل FPRO؛ لم تُقس بعد فروق frame time أو startup-to-content على جهاز المستخدم وحسابه. الهاشتاجات والتنزيل الحالي وملء الشاشة والقصص باختباراتها السابقة محفوظة، ولا ندعي إصلاح حلقات الحساب غير المؤكدة.


## البناء 20 — تحديد أندرويد الأصلي والضغطتان للدخول فقط

- خيار «تحديد النص بالقائمة الأصلية للجوال» مفعّل افتراضيًا ومستقل عن مفتاح تعديلات الصفحة. أنماط محدودة للنصوص والمنشورات والتعليقات والهاشتاجات تتجاوز `user-select:none` المعتاد. محررات النصوص تبقى على سلوكها، وأزرار الواجهة وأدوات الفيديو لا تصبح نصوصًا قابلة للتحديد. يمكن تعطيل الخيار لاستعادة أنماط الموقع.
- يبقى WebView قابلًا للضغط المطوّل ويستخدم مقابض التحديد وActionMode وقائمة النسخ الخاصة بأندرويد؛ لا حوار نسخ مصطنع أو جسر clipboard من الموقع. اعتراض `selectstart` لا يلغي السلوك الافتراضي؛ يوقف إلغاءه من معالجات الموقع الفقاعية على نص القراءة فقط، ولا يمس التحرير أو الإيماءات والتمرير.
- الهاشتاج رابط، وضغطه المطوّل في WebView لا يحدد النص بمجرد CSS. لذلك تُحفظ وجهة رابط الهاشتاج المحدد وتُزال مؤقتًا أثناء ملامسة الإصبع ليجري المحرك **التحديد الأصلي بنفسه**. تعود الوجهة قبل `pointerup`/`click` العادي، أو عند بدء التمرير أو مغادرة النافذة/تعطيل الخيار، مع مؤقت استعادة احتياطي محدود. إذا أعاد فيسبوك تدوير الرابط وكتب وجهة جديدة لا نستبدلها بالقديمة. لا تغيير دائم لوجهات الروابط ولا إعادة توجيه يدوية؛ لا استخدام لـRange لفرض تحديد نص في كود التطبيق.
- مسار الضغطتين لم يعد يستدعي `exitFullscreen` مطلقًا. يتحقق من fullscreen القياسي وWebKit وحالة native custom view قبل طلب الدخول، ويستهلك إيماءة الفيديو المعروفة دون تحويلها إلى خروج. لا تنشيط تلقائي لملء الشاشة. زر الرجوع/المشغّل الأصلي يبقى للخروج، وخيار تعطيل الضغطتين محفوظ. وجود تحديد نص نشط يمنع تشغيل إيماءة الفيديو.
- إزالة ست حالات optional chaining من السكربت نفسه حافظت على المعنى وساعدت محركات WebView الأقدم على تحليل السكربت. هذا لا يضمن توافق موقع Meta نفسه مع كل محرك قديم، وتوصية تحديث WebView باقية.
- اختبارات DOM: استقلال المفتاح واستعادته وحماية المحرر، عدم إلغاء التحديد الافتراضي، استعادة وجهة الهاشتاج قبل النقر وبعد التمرير/التعطيل، حفظ الوجهة الجديدة للعقد المعاد تدويرها، وعدم الخروج/إعادة الدخول بالضغطتين في حالات fullscreen القياسية وWebKit/native، وعدم تفعيل الفيديو أثناء تحديد النص. كل اختبارات السرعة والهاشتاج والتنزيل السابقة باقية وناجحة.
- اختبار الجهاز المحلي يستخدم **MotionEvent لضغط مطوّل حقيقي** لكل نوع نص، ويقرأ تحديد المحرك ويبحث عن أمر النسخ الأصلي عبر Accessibility. لا يستدعي `Selection.addRange` لتمرير الاختبار؛ Range يستخدم لقياس موضع الكلمة فقط. بين العناصر يلغي مقابض التحديد بلمسة فعلية على مساحة فارغة كما يفعل المستخدم.
- التجارب الأولى كشفت أن النص العادي/التعليق يعملان، لكن الهاشتاج الرابط لا يبدأ تحديدًا أصليًا؛ لم تُحسب نجاحًا. المعالجة أعلاه اجتازت اختبار الهاشتاج النهائي. أصلحت جاهزية fixture الشعار كيلا يقرأ الاختبار حالة الصفحة القديمة، وحفظت تأكيداته. فشل بكسل مؤقت في جولة سابقة لم يُحسب نجاحًا؛ الجولة النهائية بجميع التأكيدات نجحت.
- Java مجرد سؤال من المستخدم ولم نُحوّل المشروع: Kotlin وJava يعملان على Android Runtime، واختلاف الأداء يعتمد على التصميم والعمل الفعلي وWebView لا اسم اللغة وحده. تحسينات 19 محفوظة. لا تغيير لمسار الهاشتاجات أو الحلقات أو مصدر تنزيل الفيديو الحالي أو Seal.
- النص داخل الصور/Canvas ليس نص DOM قابلًا للتحديد. قد تمنع طبقات خاصة أو معالجات موقع مبكرة/أنماط inline مهمة جدًا التحديد؛ لا ادعاء بإزالة كل قيود فيسبوك أو الوصول لإطارات محمية. نجاح الاختبار المحلي لا يثبت سلوك كل تعليق في الحساب الفعلي.


## البناء 21 — التحديد داخل حاويات تفاعلية ومراجعة المحرك المرسل

المستخدم أبلغ أن التحديد لا يستجيب في حسابه رغم اختبارات 20 المحلية. لم تُلغَ شكواه ولم نعتبر الاختبارات إثباتًا لحسابه. سبب الفشل الفعلي غير معلوم دون وصف بنية العنصر؛ وجود نص داخل `role="button"`، أو منع inline مهم، أو إلغاء الأحداث، حالات مرشحة أصبح لها اختبار.

- تُجهّز كتلة القراءة الملموسة فقط، حتى 10 أسلاف، بـ`user-select:text!important` مع علامة محدودة. يصبح نص المنشور/التعليق داخل حاوية تفاعلية قابلاً للتحديد بدل حظره مع كل الأزرار. تستثنى أزرار HTML وأفعال التفاعل المعروفة بالعربية والإنجليزية والمحررات، بما فيها plaintext-only، والتنقل والوسائط. لا تغيير للنص نفسه ولا نسخ مصطنع أو Range مفروض في التطبيق.
- حراسة pointer/touch/selectstart في capture على window للنص المقروء تمنع وصوله إلى إلغاء Meta المفوض، **دون preventDefault** أو إلغاء التمرير. يبقى click العادي على سلوكه. لا يمكن التراجع عن preventDefault سبق أن نفذه معالج أقدم على window أو الوصول لإطارات محمية؛ لذلك لا ضمان لكل بنية حساب.
- تحفظ خصائص التحديد الأصلية وقيم important وتستعاد عند تعطيل الخاصية أو تجهيز كتلة أخرى، ولا تستبدل قيمة جديدة كتبها الموقع. عدد العناصر المحتفظ بها محدود ولا توجد دورة فحص للمنشورات. سجلات هذه الكتابات مملوكة فلا تطلق مسار فحص شامل إضافي. مسار الهاشتاجات السريع ومحرك الألوان وملء الشاشة للدخول فقط لم يتغيرا.
- قسم `selection` في تقرير الألوان يعرض تفعيل الخيار ووجود CSS وعدد العناصر المجهزة وثلاث قيم منطقية عن آخر نص جُهز؛ لا نصوص أو روابط أو أسماء أو CSS المصدر. إذا استمر الفشل: اضغط مطولاً على النص أولاً ثم انسخ تشخيص التلوين من الإعدادات للمقارنة، دون مشاركة محتوى الحساب.
- استفدنا من عبارات «Open the Facebook app / استخدم تطبيق فيسبوك / فيسبوك الأصلي» داخل مرشح اللافتة الموجود فقط، وبقي مرتبطًا بالمفتاح المحفوظ. لم نستخدم التقاط أي حبة زرقاء مكتوب عليها Facebook. أضفنا حراسة ضد إخفاء article يحمل role=button أو فيديو/نموذج أو شريط تنقل كامل؛ الاستعادة عبر نظامنا الحالي.

### لماذا لم نزرع FproColor/NOAPP حرفيًا؟

المحرك المرسل مفيد كمرجع، لكنه ليس بديلاً آمنًا متوافقًا مع اتفاق تلوين التفاصيل فقط:

1. `passStyles/passAttrs` يغيران خلفيات وأنماط الموقع الأصلية عالميًا؛ إزالة `fpro-rc` لا تستعيد هذه التعديلات في `off()`. العلامتان `__fproRs/__fproRa` تتجاوزان إعادة المعالجة عند تغيير اللوحة أو إعادة تدوير المحتوى. ذلك قد يلغي مزايا النظام الحالي والاستعادة.
2. تحويل `border:2px solid #1877F2` إلى `border-color:...` يحذف العرض ونمط الخط من shorthand، وقد يخفي الحلقة. `(+ra || 1)` يحوّل ألفا الصفر إلى 1 ويغير الشفافية.
3. شارة تحمل تسمية verified ليست ضمانًا أن كامل صورتها أيقونة صغيرة؛ بقيت قيود الحجم/السياق الحالية وحماية الصور. لا دليل جديد أن دائرة الحساب أو شارته تطابق القواعد.
4. إخفاء الأسلاف بحسب ارتفاعها أو اللون الأزرق فقط، وإخفاء أب «فارغ» من الأبناء غير المخفيين مع تجاهل النص المباشر، قد يخفي محتوى صحيحًا. استعادة display بإزالته لا تحفظ دائمًا الأصل المهم. لم ننقل هذا التصعيد ولا مؤقتاته الثلاثة.
5. قائمة Palette المرسلة تضم 11 إدخالاً وتفتقد الأبيض من خياراتنا الـ12؛ لم نحذف الأبيض أو نغير درجات الألوان الحالية أو لغة المشروع بصمت.

### التحقق

DOM يغطي wrapper تفاعليًا مع inline-important، وعدم إلغاء الافتراضي، وحماية زر إعجاب ذي aria-label مختلف ومحرر plaintext-only، واستعادة الخصائص، وخصوصية التشخيص، وعبارات اللافتة الجديدة وحفظ الرجوع/النموذج/الفيديو والـarticle واستعادة الإخفاء. جميع الاختبارات السابقة باقية وناجحة محليًا.

اختبار الجهاز يضع المنشور والتعليق والهاشتاج داخل `article role=button` مع user-select:none!important، ومعالجات document تلغي pointerdown/touchstart/selectstart. يستخدم ضغطًا مطولاً حقيقيًا ويؤكد تحديد الكلمة وظهور **أمر النسخ الأصلي ثم نقره عبر Accessibility**، لا نسخًا من كود التطبيق. الوصول إلى النسخ نفسه ينهي كل تحديد قبل اختبار النص التالي، حتى حين يلغي الموقع اللمسات على الفراغ. جولات سابقة فشلت عند التحديد الثاني لأن الترتيب كان ينهي الحالة بلمسة صفحة تمنعها fixture؛ لم تُعدّل تأكيدات التحديد والنسخ لتجاوزها. الجولة النهائية ما زالت **2/4** إجمالاً بالفشلين المذكورين أعلاه، وليست إصدارًا مجتازًا لكل الفحوص. تبقى تجربة الحساب الفعلية ضرورية.


## البناء 22 — استخدام المحرك المرسل للتلوين وإخفاء فتح التطبيق

موافقة المالك اللاحقة على التلوين الأوسع **تستبدل قيد التفاصيل فقط الوارد في مراجعة البناء 21**. الملف الجديد `reference-engines.js` يتضمن تكييفًا فعليًا لمحركي FproColor وFproNoapp، ويُحمّل قبل `facebook.js`، لا مجرد الاحتفاظ بالنص كمرجع.

- المفتاح «محرك التلوين الشامل وإخفاء لافتة التطبيق — الكود المرسل» مفعّل افتراضيًا؛ يحتاج تفعيل تعديلات الصفحة. اختيار لون غير تلقائي/طبيعي يفعّل التلوين الأوسع، وإيقاف المحرك يعيد المسار المحدود السابق. بقيت الخيارات اللونية الـ12.
- تُعدّل تصريحات الألوان داخل style والأنماط المضمنة ومتغيرات الأزرار/الأيقونات، مع إبقاء عروض الحدود وأنواعها وشفافية الصفر. لا تُعاد كتابة URLs أو المحددات، ولا تُفلتر الصور الشخصية. يوجد مسار شارة صغيرة معنونة كما في المرجع.
- تُحفظ الأنماط المملوكة للمحرك للاستعادة، وتُحترم تغييرات الموقع اللاحقة؛ يُستعاد لون الخلفية المملوك حتى لو عدّل الموقع لون نص العنصر نفسه. يُتجاوز تحليل الأنماط التي لم تتغير، والفحص محدود ومرتبط بالمجدول السابق دون مراقب أو مؤقت جديد.
- إخفاء لافتة التطبيق مفعّل افتراضيًا، مع احترام قيمة إيقاف محفوظة والمفتاح الرئيسي. تُستخدم عبارات الدعوة وروابط التطبيق وقرينة الزر الأزرق الصغير قرب أعلى الصفحة، مع حماية المقالات والمشغّل والنماذج والتنقل. ليس ضمانًا لاكتشاف كل صيغة يرسلها فيسبوك.
- لم يُغيّر مسار الهاشتاج السريع أو تنزيل المقطع الحالي إلى Seal أو الدخول فقط بالنقرتين إلى ملء الشاشة، ولا يدّعي هذا البناء حل بلاغ تحديد النص الفعلي.

نتيجة اختبارات DOM: نجاح التلوين الأوسع للأوراق والأنماط المضمنة، تبديل اللوحة والاستعادة وحفظ تغييرات الموقع، عرض/نوع الحدود وalpha=0، حماية الصور والمقال والفيديو والرجوع، واحترام الإيقاف. نتائج Android وروابط APK في بداية الملف.


## البناء 23 — الاستجابة لتجربة الحساب بعد نجاح ألوان 22

- يبقى المسار الشامل الذي أعجب المستخدم. العناصر المضافة والأنماط المضمنة المتغيرة وقواعد style الجديدة/المعدّلة تُلوّن في microtask التغييرات، دون انتظار 500ms للفحص الشامل. نفس المراقب يشمل head لإمساك الأوراق الجديدة؛ لا مراقب أو مؤقت جديد. العمل مقتصر على 32 جذرًا مع حدود المحرك وكاشه الحالي، وتُستبعد كتابات FPRO المملوكة وأدواته من إعادة الفحص. الهاشتاجات الفورية والفحص المؤجل للترشيح/التخطيط باقية. التحميل الأول وسياسات الرسم في WebView قد يظلان ظاهرين؛ لا نخفي الصفحة أو نعرض لقطة مزيفة لتغطية التأخير.
- إخفاء التطبيق لا يصعد إلى حاوية فيها تحكم أو SVG/صورة خارج فرع CTA، أو نصوص إضافية. يُحمى الشريط حتى عندما يكون البحث/الحساب أيقونات فقط، وتُمنع الحاويات ذات التحكمات المتداخلة من أن تصبح CTA لمجرد بدء اسمها بالعبارة. أُلغي استدلال زر أزرق يحمل اسم Facebook دون دعوة تطبيق صريحة؛ العبارات الدقيقة وروابط التطبيق باقية. حماية المقال والفيديو والنماذج والتنقل باقية.
- التحديد يجهّز أيضًا النص المباشر في div، ويستخدم دليل dir-auto في أسلاف span للتعليقات غير الموسومة article؛ إعداد اللمس مستقل عن وجود pointerdown. يُحمى contextmenu للنص المقروء من إلغائه في المستند دون preventDefault أو قائمة نسخ مصطنعة. تبقى الأزرار والمحررات والتنقل مستثناة. التشخيص يسجل نوع الحدث وعلم إلغاء سابقًا فقط، بلا النص أو أسماء الحساب.
- توسّع الاختبار الأصلي إلى ضغط مطوّل فعلي ثم Copy على المنشور والتعليق والهاشتاج وdiv مباشر، مع إلغاء contextmenu من الصفحة. نجح على Android10/15 في التشغيل النهائي. اختبارات DOM الإضافية تحمي البحث/الحساب وشريطًا بأيقونات فقط في المحركين، وتتحقق من التلوين في microtask قبل موعد الفحص المؤجل ومن touchstart وcontextmenu والتعليق دون article. اختبار اللون المحدود الأصلي ما زال يعطّل المحرك الشامل صراحةً؛ ليس إثبات بكسلات الحساب المسجل.
- لا يُعد التحديد داخل الصورة/بكسلات الفيديو نصًا قابلًا لتحديد WebView. إذا بقي الفشل على نص منشور/تعليق فعلي: اضغط عليه مطولًا ثم انسخ «تشخيص التلوين — دون بيانات الحساب»؛ لا حاجة لإرسال محتوى الحساب أو بيانات دخوله.


## البناء 24 — اللمس وإخفاء CTA ومسار المغادرة

بلاغ المستخدم بعد 23: لمس ثقيل وأحيانًا بلا استجابة، تشغيل بالخلفية لا يعمل، وإخفاء «فتح التطبيق» متأخر. لم يُقَس زمن الاستجابة في حسابه ولم نفترض أن كل التأخير من الموقع أو الجهاز.

- مسار التغييرات الفوري لا يقيس أبعاد الشارات أو الأزرار، ولا يمر على أحفاد الصفحة عند تعديل نمط body وحده. حد التلوين الفوري 24 نمطًا مضمنًا و4 أوراق صغيرة لكل دفعة، مع تأجيل بقية العمل للفحص الموجود. تُختبر دلالة الشارة والفلتر قبل أي قياس حتى في المسار الكامل؛ لا يُقاس كل data-testid عشوائي.
- الدعوة الصريحة للتطبيق تُخفى في نفس microtask، بما فيها تغيّر نص span داخل زر سبق تلوينه. لا يُسقط مرشح التغييرات أحداث النص/aria/href لمجرد أن نمط العنصر مملوك للمحرك. المسار السريع بلا قياسات هندسية؛ طي الأغلفة النقية يبقى في الفحص الكامل مع حماية البحث/الحساب.
- التحديد لا يعتبر خلفية المشغّل نصًا لمجرد وجود تعليق في أحفادها، ولا يمنع أحداث المؤشر عن الروابط الرسمية غير الهاشتاج. على WebView يُتحقق من وقوع اللمس على مستطيل النص نفسه؛ تجهيز الأنماط لا يتكرر في pointerdown وtouchstart عند توفر Pointer Events. حماية لمس القراءة الأصلية باقية، كما أن تجربة الحساب لتحديد النص لم تُثبت بعد.
- خيار المغادرة الموجود هو **صورة داخل صورة** وليس خدمة صوت مع قفل الشاشة. يصل تلميح تشغيل منطقي فقط من أحداث الفيديو إلى أندرويد، ويُقبل إذا كانت الصفحة العليا Facebook/Messenger؛ لا يعرض الجسر نصوصًا أو ملفات أو كوكيز أو تشغيل تطبيقات. لا يبدأ فيديو متوقف تلقائيًا. تُعاد مزامنة الحالة مع استعلام الصفحة وعند الاستئناف.
- Android12+ يجهز auto-PiP قبل المغادرة؛ Android8–11 يستخدم الحالة المحفوظة لطلب متزامن عند الرئيسية بدل انتظار evaluateJavascript بعد مغادرة Activity. تُحمى حالة انتقال PiP من web.onPause المبكر. الإيقاف والإعدادات وتسليم Seal تلغي الأهلية، وتبقى إعدادات/أذونات النظام شرطًا. لا توجد خدمة foreground لتشغيل صوت الشاشة المقفلة ولا ندّعي وجودها.
- أُضيف فيديو H264 أحمر مولد محليًا مدته ثانيتان وحجمه2257 بايت ضمن androidTest فقط، لا APK التطبيق. يتأكد الاختبار من فك الفيديو وتشغيله ومن انعكاس ذلك في حالة أندرويد، يضغط Home فعليًا، ثم يشترط PiP النظام وتقدم ساعة الفيديو دون إيقاف. لا تُزيَّف حالة التشغيل ولا تُستبدل API النظام. عنوان history الصريح للصفحة الاصطناعية ضروري في الاختبار كي لا تظل about:blank ويرفضها حارس الأصل؛ الحارس الإنتاجي لم يُضعف.
- اختبارات DOM الجديدة تثبت صفر قراءات هندسية في المسار السريع، وعدم اجتياز feed عند تغيير نمط body، والإخفاء الفوري مع بقاء البحث، ومرور اللمس لخلفية المشغّل/رابط الحساب، وتحديث تلميح التشغيل/الإيقاف دون انتظار المغادرة. لا تعادل هذه نتائج قياس سلاسة الحساب المسجل.


## البناء 25 — طلب الصوت فقط ووميض CTA وAMOLED وانحدار التحديد

المستخدم أكد الآن أن التحديد كان يعمل سابقًا ثم تراجع، ووضح أن الخلفية تشمل PiP وزر سماعة لإخفاء النافذة والصوت مع الشاشة المقفلة. هذا يتجاوز PiP وحده في24؛ لا نُبقي قيد «لا توجد خدمة صوت» كوصف للحالة الجديدة.

- `AudioPlaybackService` خدمة غير مصدّرة من نوع mediaPlayback، لا تعمل إلا باختيار المستخدم. تستخدم MediaSession للتحكم بالمشغّل الحقيقي نفسه، مع إشعار تشغيل/إيقاف مؤقت/إنهاء، وإذن إشعار عند الطلب على Android13+. لا تنشئ تقدمًا أو قائمة تشغيل مزيفة، ولا تستخرج الروابط المحمية أو تنزّل المقطع داخليًا. التركيز الصوتي يُترك لمشغّل WebView بدل طلب تركيز ثانٍ ينافسه.
- زر السماعة في PiP يعيد Activity عبر PendingIntent، يفعّل صوت المقطع الحالي الذي يعمل ويزيل كتمه بطلب المستخدم، يبدأ الخدمة ثم يخفي المهمة بدل ترك نافذة PiP. إشعار الخدمة يعيد الفيديو. WebView يبقى نشطًا فقط أثناء الصوت المصرّح به؛ `onWindowVisibilityChanged` لا يعلّق محتواه عند قفل الشاشة خلال هذا الوضع. لا تُستبدل getters الخاصة بـdocument.hidden ولا توجد حلقة فرض play. تتوقف الخدمة عند الإنهاء/قتل العملية ولا تعيد تشغيل نفسها تلقائيًا. WakeLock يُحرر عند الإيقاف المؤقت/الإنهاء، والخدمة تنتهي بعد10 دقائق من الإيقاف المؤقت. تعاد حالة الكتم/الصوت الأصلية عند الخروج من الوضع.
- `early-start.js` عبر AndroidX WebKit DOCUMENT_START_SCRIPT يبدأ أدوات الصفحة عند ظهور body، ويثبت حراس أحداث window قبل سكربتات الموقع. قبل دعم هذا المسار، كان الحقن عند commit/finish قد يسمح بإطار CTA أول. التغييرات اللاحقة تبقى في مسار microtask المحدود. المحركات غير الداعمة تحتفظ بالمسار السابق؛ يظهر علم documentStart في التشخيص، ولا وعد مطلق بزوال كل وميض على كل محرك/نسخة موقع.
- حماية التحديد المبكرة تسبق معالجات window التي قد تلغي الضغط الأصلي، وتشترك في تجهيز النص والهاشتاج دون إلغاء default. أزيل رفض النص المباشر لمجرد أن caretRangeFromPoint لا يستطيع إرجاع عقدة قبل تجاوز user-select:none، مع إبقاء فحص مستطيل النص عندما يتوفر وحماية خلفية الفيديو/الروابط/الأزرار. نجاح النص الأصلي والنسخ محليًا لا يثبت الحساب؛ لا نعلن حل الانحدار الفعلي قبل تجربة المستخدم.
- AMOLED يجعل الداكن فعالًا بذاته في إعدادات الصفحة، ويستبدل متغيرات أسطح Meta المعروفة وخلفيات الأجزاء الدلالية بالأسود، دون فلتر عكسي للصور/الفيديو. أسطح Compose كلها سوداء أيضًا مع إزالة صبغة الارتفاع، حتى مع الألوان الديناميكية؛ قراءة revision تسبق بناء الثيم لتحديثه فورًا.
- الاختبار الأصلي يستخدم مقطع H264/AAC نغمة مولدًا محليًا (11720بايت، androidTest فقط). يرسل PendingIntent زر السماعة فعليًا، يتحقق من خدمة foreground واختفاء PiP، يطفئ الشاشة ويتأكد من PowerManager غير تفاعلي وساعة فيديو متقدمة وAudioManager نشط، ثم ينهي الخدمة بزر الإشعار. فشل المحاولة الأولى عند الشاشة المقفلة كشف تعليق WebView عبر إخفاء النافذة وعولج في d269ea5. أخطاء teardown التالية كانت من ترشيح ActivityScenario لأحداث lifecycle حسب Intent.action بعد أن غيّره PendingIntent الحقيقي؛ أعيد Intent المطابق للاختبار عند التنظيف دون إزالة أي تأكيد تشغيل/صوت/قفل. راجع [مصدر AndroidX الرسمي](https://github.com/android/android-test/blob/main/core/java/androidx/test/core/app/ActivityScenario.java).
- اختبار API35 المبكر يراقب أول requestAnimationFrame للـCTA، يتحقق من البطاقة السوداء والبحث الظاهر ومن حدث ضغط أولي على النص أمام إلغاء window. على API29 غير الداعم يُتخطى هذا الاختبار فقط، بينما يبقى اختبار الضغط المطول/Copy الحقيقي واختبار PiP/الصوت/قفل الشاشة مطلوبين وناجحين.

**الاستخدام:** شغّل الفيديو ثم غادر بالرئيسية للصورة داخل صورة. اضغط السماعة للصوت فقط واسمح بإشعار التحكم؛ أو استخدم «صوت فقط — استمرار عند قفل الشاشة» من الإعدادات. اضغط الإشعار للعودة للفيديو، أو زر إنهاء لإيقاف الخدمة. لا تغلق صفحة المقطع أو تنه التطبيق إذا أردت استمراره. قيود البطارية والموقع وتغير DOM قد تؤثر في حساب فعلي رغم اجتياز المقطع المحلي.
