# FPRO 69 — الرجوع وملكية إخفاء الدعوة وحفظ الجلسة

التاريخ: 2026-11-02. تعديل تدريجي بإذن صاحب التطبيق، وليس تحويلًا إلى Nav3 أو إعادة كتابة WebView. لم تُعدّل ميزة النسخ المؤجلة أو الثيمات أو التنزيل أو بروتوكول الصوت/PiP أو منطق دوران النسخة 67.

## قبل التعديل

- الفحص التاريخي على أندرويد 13 [41349577662](https://github.com/abdulrahmanalmikhlafi736-cmd/goldbook/actions/runs/41349577662) أثبت أن محرك 62 يستطيع إخفاء حاوية فيديو Shadow DOM كبيرة كاملة. فكّ الفيديو 14 إطارًا، وON أخفى المالك وOFF أعاده. هذه صفحة محلية، لا إثبات لبنية حساب فيسبوك.
- أُعيد إثبات العيب محليًا قبل تعديل الإنتاج؛ بقيت الأدلة التاريخية دون تغيير. أداة `audit-prompt-viewer.cjs` أصبحت تقرأ مصدر 6e5c8ef صراحةً، حتى لا يصبح نجاح فحص العيب القديم ادعاءً عن الإنتاج الجديد.

## التعديلات

### 1. ملكية إخفاء «فتح التطبيق»

- التحقق من حجم **المرشح نفسه**، وليس الحاوية الأم فقط (حد الارتفاع 160px).
- حماية حاويات الوسائط المعروفة، وجذور Shadow DOM المفتوحة ومضيفات العناصر المخصصة والخلفيات المصورة؛ زيارة فرعية محدودة حتى 32 عنصرًا، بعد التعرف على تسمية الدعوة فقط، لا مسح الخلاصة بحثًا عن الظلال.
- Shadow DOM المغلق غير قابل للفحص العام؛ حماية الحاوية الكبيرة تحدّ من هذا المثال، ولا نزعم اكتشاف كل جذر مغلق صغير.
- إزالة إخفاء CSS العام المبني على aria-label وحدها. CSS الجديد يخفي فقط عناصر ثبتت ملكيتها برمجيًا. الاكتشاف يبقى متزامنًا عند التفعيل وفي MutationObserver قبل الرسم؛ لا مؤقت أو rAF يؤخر الدعوات الجديدة.
- إعادة فحص تغيّرات style للعناصر المخفية، فلا يُتجاهل تحول زر صغير إلى حاوية كبيرة بحجة أن display ما زال none.
- الحفاظ على تقييد جذور الطفرات ومنع إعادة مسح الخلاصة مع تغيّر opacity/classes لأسلافها. اختبار 1200 منشور: صفر تعداد لأحفاد الخلاصة في دفعات تغيّر الأسلاف.

**حدود:** الحماية التحفظية قد ترفض دعوة ذات تركيب غير مألوف أو خلفية مصورة. لا يمكن ضمان إخفاء جميع تصميمات فيسبوك أو انعدام اللمحات على حساب المستخدم من صفحات محلية فقط. قبول الإصلاح يتطلب بقاء المحتوى ظاهرًا وإخفاء الدعوة دون عودة ثقل 62.

### 2. الرجوع

- الإعدادات وملء الشاشة الأصلي أولًا، كما كانا.
- قرار JavaScript أولي للقراءة فقط، وليس تنفيذ إغلاق ينتظر callback قد يصل بعد رجوع آخر.
- استعلام واحد أثناء اتخاذ القرار؛ مهلة أصلية 1200ms تفصل الاستجابة المتأخرة عن مسار السجل. المهلة لا تصلح renderer معطلًا؛ تطلب الرجوع الأصلي ولا تنتظر JavaScript إلى الأبد.
- إلغاء التذكرة والمهلة عند بدء صفحة جديدة، أو استبدال renderer، أو pause/destroy. التحقق من هوية WebView ورقم تحميل الصفحة وحالة الواجهة قبل تنفيذ نتيجة. قرار العارض يتضمن رابط DOM، ولا تنفذ أوامر إغلاق DOM إذا تغيّر ذلك الرابط؛ لا نعتمد على مساواة رابط native قد يتأخر عن تحديث SPA.
- إعطاء سجل حقيقي سابق أولوية على تحميل الرئيسية من مسار الرسائل. fallback الرئيسية بقي فقط عند فتح الرسائل دون تاريخ رجوع.
- BackHandler المعتاد ينفذ عند إتمام الرجوع؛ لم يُضف PredictiveBackHandler ينقل الصفحة أثناء إيماءة قد تُلغى.

**حدود:** أُبقي منطق إغلاق نافذة الموقع المعروفة؛ لم تُخترع أحداث لمس أو آلية تحديث أصلية. ليس كل تغيير داخلي لخلاصة Facebook إدخالًا مستقلًا في سجل WebView، ولا يضمن هذا التعديل وحده استعادة المنشور على الحساب.

### 3. حفظ الحالة

- `WebViewStateSnapshot`: حزمة WebView بحد 256KiB، منفصلة عن ملف الجلسة الخاص ذي حد 2MiB وعن بيانات الموضع الصغيرة.
- `WebViewCompat.saveState(web, bundle, maxBytes, false)` بعد فحص `SAVE_STATE`؛ المكتبة الموجودة 1.16.0 ولا تُضاف تبعيات جديدة.
- المسار القديم: عدم التقاط سجل يتجاوز 128 إدخالًا، وقياس Bundle الناتجة وعدم قبولها إذا تجاوزت الميزانية. هذا المسار لا يستطيع تجنب تكلفة الالتقاط الأولية لسجل صغير ذي إدخال كبير.
- لا تعديل/محو للسجل الحي ولا تحليل لكتل PageState الداخلية. عند فشل الحفظ يستمر التصفح دون checkpoint جديد.
- منع تكرار كتابة نفس الموضع مع نفس حجم السجل وفهرسه بين pause/stop؛ تنظيف مفاتيح المقارنة عند مسح الجلسة.
- ليست هذه آلية لحفظ كل DOM أو مشغل الفيديو أو ترتيب الخلاصة الحي بعد موت العملية.

### 4. العمل الدوري

- تقييد استعلامات رأس الصفحة والحفظ الدوري بحسب استئناف الشاشة والإعدادات وPiP والصوت وملء الشاشة.
- إبقاء مسار مزوّد WebView القديم الذي يحتاج استطلاعًا بديلًا لتقرير التشغيل؛ عدم تغيير تشغيل الخدمة الصوتية أو onStop/PiP.
- عدم إرسال استعلامات جاهزية دورية أثناء pause، وعدم إضافة إعادة تحميل تلقائية أو مكتبات تنقل جديدة.

المجموعة المستهدفة ذات 11 اختبارًا تضم:
- حماية مالك فيديو Shadow DOM كبير مع إخفاء CTA الحقيقي وOFF وإبقاء المشغل نفسه.
- الرجوع من مسار الرسائل إلى السابق بدل تحميل الرئيسية.
- إشغال renderer فعليًا 2400ms، ضغطتي Back أثناء القرار، مهلة native 1200ms، ثم التحقق من رجوع واحد وعدم تنفيذ نتيجة متأخرة ثانية.
- إغلاق نافذة الموقع باستدعاء معالجها دون مغادرة الصفحة.
- حفظ/استعادة سجل محدود الحجم دون تغيير السجل الحي، وحالة كثيرة الإدخالات/البيانات مع مراعاة حدود المزوّد.
- اختبارات موضع الخلاصة الأربعة السابقة.
- حمل ألوان الفيديو دون مسح عالمي متكرر.
- PiP فعلي، فك صوت AAC، خدمة صوت في المقدمة مع الشاشة مطفأة، ثم إيقافها من الإشعار.

**كيفية تجهيز الرجوع:** تستخدم الاختبارات الجديدة روابط HTTPS حقيقية داخل WebView، لكن استجابتها HTML محلية عبر `shouldInterceptRequest`، مع تمرير callbacks التنقل إلى عميل الإنتاج ولمسات فعلية. لا توجد اتصالات بحساب فيسبوك أو ملفات تسجيل دخول. أُزيل افتراض أن سجل `loadDataWithBaseURL` الافتراضي يماثل التنقل العادي متعدد الإدخالات.

### النتائج غير الناجحة محفوظة، وليست مخفية

- جولات التجهيز الأولى فشلت. أُصلح انتظار تسجيل BackHandler، واستعمال خاصية Compose المفوضة كحقل Boolean عبر reflection، ومقارنة JSON escaped مع string مفكوك، وتجهيز تاريخ التنقل. لم نغير الوجهة المطلوبة للرجوع لتوافق نتيجة خاطئة.
- أُحكم قرار الرجوع في 84c24a8 ليستخدم رابط العارض لأوامر DOM بدل إسقاطه بمقارنة native URL قديمة. لا نعتبر هذا وحده إثبات سبب مشكلة الحساب.
- حدثت نتيجة PiP متقطعة في جولة سابقة: الدخول نجح لكن الفيديو بقي muted عند العينة. كما حدث اختلاف بين عينتي بدء فيديو منفصلتين عند loop؛ صار أخذ عينة الجاهزية والتشغيل والإطارات ذريًا دون تخفيف شروط الحمل اللاحقة. **لم نغيّر كود الصوت لادعاء إصلاح ذلك التقطع**؛ الجولتان النهائيتان ناجحتان ولا تضمنان جميع التوقيتات والأجهزة.
- فحص الترقية الأوسع **ما زال FAIL** في اختبار النسخ/التعليقات المؤجل `nativeCopyIsAvailableForPostsAndHashtagsButNotComments`: [41397147230](https://github.com/abdulrahmanalmikhlafi736-cmd/goldbook/actions/runs/41397147230). لم يُعدّل كود التحديد لمعالجة أو إخفاء هذا الفشل.
- مصفوفة الأجهزة الواسعة 29/35/36 لم تكن مكتملة وقت حفظ الأدلة؛ ليست هناك دعوى أن جميع اختبارات المشروع خضراء.

الأدلة الآلية وحالات التشغيل: `BACK-MEDIA-SESSION-69-EVIDENCE.json`.
